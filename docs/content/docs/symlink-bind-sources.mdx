This page describes a change that exists only in the
[wyrd-company fork](https://github.com/wyrd-company/sockguard).

`allowed_bind_mounts` compares a bind source as a string. The daemon mounts it
through the host filesystem and follows every symlink on the way. A source
such as `/srv/workspaces/a/link` passes a `/srv/workspaces` entry while
`link` points at `/`. The fork resolves every symlink in the source and checks
the result against the allowlist again. A source that passes the string check
and resolves outside every entry is denied.

## Where sources are resolved

| Endpoint | Fields |
| --- | --- |
| `POST /containers/create` | `HostConfig.Binds` sources, `HostConfig.Mounts` entries of type `bind`, `Config.Volumes` keys that Podman reads as binds, `upperdir`/`workdir` overlay options in a `Binds` entry, and the bind device and overlay directories of a `local` volume in `Mounts[].VolumeOptions.DriverConfig` |
| `POST /libpod/containers/create` | `mounts[]` bind sources, `rootfs`, `overlay_volumes[].source`, `upperdir`/`workdir` options on `overlay_volumes` and `volumes`, `init_path` |
| `POST /volumes/create`, `POST /libpod/volumes/create` | the bind device and overlay directories of a `local` volume |
| `POST /containers/{id}/start`, `POST /containers/{id}/restart` and the libpod equivalents | the bind sources and local-volume bind devices the daemon reports for the container; see [Re-check at start and restart](#re-check-at-start-and-restart) |

These keep the string check only:

- **Service create and update.** A swarm task's source resolves on the node
  that runs the task, which the proxy cannot see.
- **Plugin install and upgrade.**
- **Device paths** (`HostConfig.Devices`, libpod `devices`) and the device
  node of a `local` volume that mounts a host filesystem type (for example
  `{"type":"ext4","device":"/dev/sda1"}`). These are not binds, and the usual
  spellings (`/dev/disk/by-uuid/...`) are symlinks.

## Resolution rules

- Every component is resolved, including intermediate directories and
  relative targets that contain `..`.
- A `..` is applied the way the kernel applies it: to the real parent of what
  the walk has reached, after the symlink before it is followed. A source that
  is spelled with `..` is checked both as written and in its cleaned form.
  dockerd and libpod mount the cleaned form. A `local` volume device or overlay
  directory reaches the kernel as written, and Podman's compat create runs
  `os.MkdirAll` on a `HostConfig.Binds` source as written. So `/srv/workspaces/link/../x`, with
  `link` pointing at `/mnt/other`, is checked as `/mnt/x` too and is denied.
- Allowlist entries are resolved too, so an entry that is itself a symlink
  (`/srv/workspaces` -> `/mnt/data/workspaces`) still covers the sources under
  it.
- A source that contains no symlink resolves to itself, so an ordinary path
  that passes the string check passes as before.
- A part of the source that does not exist yet is taken as a directory that
  will be created, and the rest of the source is resolved from there. dockerd
  creates a missing `HostConfig.Binds` source as a directory at start, so such
  a request still works.
- Each directory that would be created must itself be under an allowlist
  entry, or be a parent of one. `os.MkdirAll` creates a missing component
  before a later `..` leaves it, so the final path alone does not show every
  directory a source creates. `/srv/workspaces/a/../b` with `a` missing
  creates `/srv/workspaces/a` and is allowed; the same spelling that reaches a
  missing directory outside the entry through a symlink or a `..` is denied
  with `... creates directory "<path>", which is not allowlisted`.
- An allowlist that contains `/` allows every source, so nothing is resolved.

Each failure has its own deny reason:

| Reason | Cause |
| --- | --- |
| `... resolves to "<path>", which is not allowlisted` | the resolved source is outside every resolved allowlist entry |
| `... creates directory "<path>", which is not allowlisted` | a missing directory on the way would be created outside every entry and is not a parent of one |
| `... cannot be resolved: dangling symlink at "<path>"` | a symlink on the path points at something that does not exist |
| `... cannot be resolved: symlink loop at "<path>"` | more than 40 symlinks were followed, the kernel's limit |
| `... cannot be resolved: permission denied at "<path>"` | the proxy user may not look up a directory on the path |
| `... cannot be resolved: lookup failed at "<path>"` | any other lookup error, for example a file in the middle of the path |

## Deployment requirement

The proxy resolves paths in its own mount namespace. The result is correct
only when the proxy sees each allowlisted host path at the same path as the
host. Mount each allowlisted root into the proxy container read-only, at the
same path:

```yaml
services:
  sockguard:
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - /srv/workspaces:/srv/workspaces:ro
```

At startup, the proxy checks every `allowed_bind_mounts` entry in
`request_body.container_create` (also used by volume create) and
`request_body.libpod_container_create`, in the base config and every client
profile. A missing entry logs one warning per entry per block, naming the
block and path. An existing file, such as a socket, is valid. A permission
error has a distinct message at the same severity. Other lookup failures
are reported separately. Service and plugin roots are not checked here.

In a Docker `container_create` block with `apply_workspace_exceptions: true`,
a missing or inaccessible allowlist entry is an ERROR and startup fails.
When `workspace_exceptions.file` is set, `workspace_root` and every
`per_workspace_roots` entry must also be existing canonical directories.
Missing, inaccessible or non-directory workspace roots stop startup. Each
visibility failure names the path and says: `mount it read-only at the same path`.
The same checks run on config reload: an ERROR rejects the replacement and
preserves the running config and policy generation. Warning-only blocks keep
warning behavior and permit the reload.

When a warning-only block cannot see a path, the source resolves to itself
(the missing-path rule above) and only the string check applies. The proxy
image runs as UID 65532 with no capabilities, so every
directory on the way to a source needs search (`x`) permission for that user.
Without it the request is denied with `permission denied`.

## Gap between create and start

The daemon resolves the source again at every start, follows symlinks, and
keeps the unresolved path in `docker inspect`. This was tested on dockerd
29.9.2: a container was created with a real directory as its source, the
directory was replaced with a symlink to a directory outside it, and
`docker start` mounted the outside directory. After the symlink was replaced
with the real directory again, the next start mounted the original directory.

A check at create alone therefore passes a real directory that is replaced
with a symlink after create. To replace a component, a process needs write
access to its parent directory:

- A client with write access to the whole allowlisted root can replace any
  path under it, at any time.
- A container that has a subfolder of the root mounted read-write can replace
  anything under that subfolder while it runs, then wait for its next start.
  It cannot replace the subfolder itself.

The check at create stops a symlink that already exists when the container is
created: a planted link, or a mount in a configuration file that names a link.
The re-check below covers a replacement between create and a start or restart
that passes through the proxy.

## Re-check at start and restart

Before the proxy forwards a start or a restart, it reads the container from
the daemon with `GET /containers/{id}/json` and applies the create check
again to each bind source and local-volume bind device the daemon reports. The routes are:

- `POST /containers/{id}/start` and `POST /containers/{id}/restart`, with and
  without an API version prefix
- `POST /libpod/containers/{name}/start` and
  `POST /libpod/containers/{name}/restart`, with and without a version prefix

The container inspect and each volume inspect go through the same upstream
connection as the proxied request, with its existing timeouts. Podman serves
the same Docker-compatible inspect routes, so libpod starts are read the same way.

The sources are the `Mounts` entries of type `bind`, the sources of
`HostConfig.Binds`, and the `HostConfig.Mounts` entries of type `bind`. A
`Binds` or `Mounts` source is checked as written as well as cleaned, as at
create. For every `Mounts` entry of type `volume`, the proxy reads
`GET /volumes/{name}`. A `local` volume with bind options contributes its
device paths, parsed by the same classifier as create, checked as written
and cleaned, after resolution, and for directories the walk would create.
A nonlocal driver or a local volume without bind options is unchanged. The
volume's mount point is not used as its device.

The allowlists are the active policy's
`request_body.container_create.allowed_bind_mounts` and
`request_body.libpod_container_create.allowed_bind_mounts`. Both apply to both
route families, because the daemon mounts the same source whichever route
created the container. A source is checked under each allowlist that admits
it as written, and passes when one of them also admits it after resolution.

In a block without `apply_workspace_exceptions`, the re-check keeps the
no-narrowing rule:

- A source that no allowlist admits as written passes. Such a container was
  not created under this policy, for example by another client or before the
  allowlist changed.
- When neither allowlist is set, or either one holds `/`, no source can fail
  the re-check, so the proxy does not read the container or any volume at all.
- A source that is unchanged since create resolves as it did at create.

In a block with `container_create.apply_workspace_exceptions: true`, every
start and restart requires exactly one workspace header, using the same
reader and key rules as create. The inspected container must have no
opposite-kind label; a same-kind label may be absent or exactly equal to the
header workspace `W`. Both labels are denied, including equal or empty
opposite-kind labels. Exec has a separate, stronger target-label rule.

Every bind source and local-volume bind device must stay inside `W`'s own
folder under every `per_workspace_roots` entry, or follow the base allowlist
outside those roots. Extra bind sources apply only under the devcontainer
header with `devcontainer.local_folder` present and byte-equal to `W`,
when the current inspected container passes the current exceptions
snapshot's create-equivalent match: a valid entry, a workspace bind mount,
and agreement of every inspected source. A named volume alone does not
supply the required workspace bind mount. Unlabeled BASE start/restart
remains allowed, but unlabeled and throwaway requests get no extras, even
with an own-`W` bind.
Own socket and staging folders count as inside `W`. Base and extra entries
are resolved like create allowlists; `W`'s folders are never resolved as
allowlist entries. See [Workspace identity](/workspace-exceptions#workspace-identity).

Each failure has its own reason and reason code. `<action>` is
`container start`, `container restart`, `libpod container start` or
`libpod container restart`.

| Reason code | Reason | Cause |
| --- | --- | --- |
| `container_start_bind_source_denied` | `<action> denied: bind mount source ...`, then the create reasons above | a source fails the create check now |
| `container_start_volume_inspect_failed` | `<action> denied: volume "<name>" could not be inspected to re-check its bind devices` | a volume lookup failed: transport, non-200 status, invalid or missing inspect fields, unreadable body, or body larger than 8 MiB |
| `container_start_workspace_missing` | `<action> denied: the request names no workspace ...` | neither workspace header is set in an opted-in profile |
| `container_start_workspace_ambiguous` | `<action> denied: the request names more than one workspace` | both headers or a repeated header |
| `container_start_workspace_invalid` | `<action> denied: the workspace header does not name a valid workspace` | empty, invalid, missing or noncanonical workspace folder |
| `container_start_workspace_label_mismatch` | `<action> denied: workspace label <label> disagrees with the request's workspace [kind]` | an opposite-kind or unequal same-kind label |
| `container_start_bind_source_outside_workspace` | `<action> denied: bind mount source ...`, naming the failed workspace bound or resolution | invalid device, or bind source or local-volume device outside the current workspace scope |
| `container_start_inspect_failed` | `<action> denied: container "<id>" could not be inspected to re-check its bind sources` | the inspect failed: a transport error, a status other than 200 (a missing container included), a body that cannot be decoded or one larger than 8 MiB |

Both inspect failures fail closed. The container inspect cause is logged at
warning level. Volume failures expose only the volume name; driver-option
values and dependency error text are not logged. Header-validation and
label-kind reasons never quote header values.

The daemon's re-resolution of `HostConfig.Binds` was measured on dockerd
29.9.2. `TestAcceptance/LocalVolumeDeviceReresolution` also measured local-volume
bind-device re-resolution on Docker 29.9.2 with both containerd and classic
image stores. The unchanged device starts through the proxy; replacing it
with a symlink into another owned directory is denied at proxy start. A
separate direct-daemon control observes the mounted marker change from the
original directory to the replacement. Proxy denial alone is not mechanism
proof. Other Engine versions and separate BuildKit workers are unproven.
The baseline profile omits restart; explicitly named route-enabled variants
provide inspected-restart evidence separately from baseline route denial.

## Gaps that remain

- **The start race.** A writer that runs at the same time can replace a
  component in the few milliseconds between the proxy's re-check and the
  daemon's mount.
- **Starts that do not pass through the proxy.** A restart the daemon does by
  itself under a restart policy, and the starts after a daemon or host reboot,
  are not checked. `require_no_restart_policy` controls whether a create
  request may set one; see
  [Workspace exceptions](/workspace-exceptions#restart-policy).
- **A compromised client that can write every component below the
  allowlisted root.** It can replace any component under the root at any
  time, so neither check binds it. In a Menagerie deployment, this client is
  Menagerie itself.
- **Podman routes that start or prepare a container another way.**
  `POST /libpod/containers/{name}/init`, `POST /libpod/pods/{name}/start`,
  `POST /libpod/pods/{name}/restart`, `POST /libpod/containers/{name}/restore`
  and kube play are not re-checked.
- **Sources the create check covers that the inspect does not report as
  binds or local-volume bind devices.** Overlay directories of a `local`
  volume, and the libpod `rootfs`, `overlay_volumes`, overlay `upperdir`/`workdir` options and
  `init_path`, are checked at create only.
